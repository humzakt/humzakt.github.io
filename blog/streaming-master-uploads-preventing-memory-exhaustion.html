Streaming Master Uploads to Disk: Preventing Memory Exhaustion in Video Pipelines

By Humza Tareen August 3, 2026 · 8 min read
Node.js Next.js Streaming Video Pipelines Performance

When processing high-definition video assets in modern web applications, memory management is frequently the silent bottleneck that causes production servers to crash unexpectedly under load. In our AI video platform (which includes Variant Multiplier and Hook Machine), processing master video uploads originally relied on standard form-data parsers that buffered incoming files directly in memory before writing them to disk. As video uploads scaled beyond 10 MB, servers encountered sudden out-of-memory (OOM) exceptions and generic "Expected a 'video' file field" multipart parsing errors.

In-memory file buffering scales linearly with upload size. Streaming to disk turns memory consumption into a flat constant.

The In-Memory Buffering Bottleneck

Standard HTTP body parsers in frameworks like Next.js often store incoming file payloads in RAM buffers (such as Buffer.concat()) during request ingestion. While this approach works reliably for small images or JSON payloads, video files introduce distinct challenges:

  • Memory Spikes: Concurrent uploads of 50 MB to 200 MB master videos quickly consume node process heap allocations, triggering garbage collector stalls and eventual OOM crashes.
  • Parser Payload Caps: Built-in body parsers enforce rigid memory buffer limits. Exceeding these limits truncates streams prematurely, confusing boundary parsers and returning unhelpful form field validation errors like "Expected a 'video' file field".

Refactoring to Disk Streaming

To resolve this, we refactored the master video ingest pipeline to stream incoming request chunks directly onto disk storage using Node.js ReadableStream and temporary file descriptors, bypassing process memory entirely:

// Stream incoming upload chunks directly to disk
import { createWriteStream } from 'fs';
import { pipeline } from 'stream/promises';
import { Readable } from 'stream';
import { join } from 'path';
import { tmpdir } from 'os';

export async function handleMasterUploadStream(req: Request, filename: string): Promise<string> {
  if (!req.body) throw new Error("Missing request body stream");

  const targetPath = join(tmpdir(), `master_${Date.now()}_${filename}`);
  const writeStream = createWriteStream(targetPath, { flags: 'w' });
  const nodeStream = Readable.fromWeb(req.body as any);

  // Pipe directly to disk with zero in-memory buffer aggregation
  await pipeline(nodeStream, writeStream);
  return targetPath;
}

Key Pipeline Hardening Steps

  1. Stream Chunking: Ingesting chunks incrementally keeps RAM consumption flat (typically under 15 MB) regardless of whether the master file is 10 MB or 2 GB.
  2. Disk Cleanup Lifecycle: Temporary files are tracked in a transient registry and automatically cleaned up if processing fails or succeeds, avoiding disk fill-up incidents.
  3. Explicit Route Configs: In Next.js App Router API handlers, disable default body parsing for raw file endpoints to delegate stream control directly to Node.js stream utilities.

What I'd do differently

I would implement direct signed URL uploads to GCS earlier in the architecture lifecycle. While streaming to local node disk solved process OOMs, streaming directly from browser to cloud storage eliminates Node.js proxying altogether, as discussed in Streaming AI Video.

The pattern: stream everything over 5MB

Master video ingestion requires treating payloads as byte streams, never in-memory byte arrays. Paired with Pre-Spend Guards and Seam-Free Video Splicing, stream-to-disk ingestion ensures high-resolution video tools remain stable under production traffic.
