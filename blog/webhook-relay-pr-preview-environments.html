Webhook Relay: Routing External Callbacks to PR Preview Environments

By Humza Tareen July 21, 2026 · 6 min read
Webhooks DevOps Microservices Node.js Infrastructure

The internal dev platform spins up an isolated backend for every pull request — its own database, its own service URLs, its own frontend preview. That works beautifully until an external service tries to call you back.

Replicate sends a webhook when your video generation completes. Stripe sends one when a test payment settles. Your AI model provider sends status updates on long-running jobs. In production, there is one webhook URL registered with each provider. In PR preview land, there are forty — one per open pull request — and none of them are reachable from the public internet without exposing every preview to every callback.

We built a webhook relay service: a lightweight Node.js proxy that receives inbound external webhooks at a stable public endpoint, inspects routing metadata, and fans them out to opted-in PR preview environments. It solved the callback routing problem without registering per-PR URLs with every external provider.

Production has one door. Preview environments need forty doors behind one address — the relay is the lobby.

The problem in production vs preview

Dimension Production PR preview
Webhook URL count 1 per provider 1 per PR × N providers
URL stability Permanent Ephemeral (PR lifetime)
Provider registration Manual, audited Impossible at PR scale
Signature verification Against known secret Must forward original signature
Routing key Implicit (only one backend) Must extract from payload or header

Naive approaches fail quickly. Registering each PR preview URL with Replicate does not scale and leaves stale URLs when PRs close. Tunneling every preview through ngrok is a security nightmare. Polling instead of webhooks adds latency and wastes API quota on a GPU-heavy platform where generation status matters in seconds, not minutes.

Architecture: the webhook relay service

The relay is a standalone repo — a small Fastify service deployed to the dev stack alongside the internal dev platform. It exposes one public endpoint per webhook provider type:

External provider (Replicate, Stripe, etc.)
        │
        ▼
┌─────────────────────────┐
│   Webhook Relay Service  │  ← stable public URL
│   (signature verify)     │
└───────────┬─────────────┘
            │ route by payload/header
     ┌──────┼──────┐
     ▼      ▼      ▼
  PR-142  PR-187  dev-stack
  preview preview  (default)

Three responsibilities, kept deliberately separate:

  1. Receive and verify — validate provider signature against the relay's shared secret
  2. Route — extract target environment from payload field or custom header
  3. Forward — POST to the target preview URL with original headers preserved
interface RelayTarget {
  environmentId: string;       // e.g. "pr-142" or "dev"
  webhookUrl: string;          // internal preview backend URL
  optedIn: boolean;
  lastHealthCheck?: ISO8601;
  healthy: boolean;
}

async function handleInboundWebhook(
  provider: WebhookProvider,
  req: IncomingMessage,
  rawBody: Buffer,
): Promise<RelayResult> {
  verifySignature(provider, req.headers, rawBody);

  const routeKey = extractRouteKey(provider, req.headers, rawBody);
  const targets = await registry.getTargets(provider, routeKey);

  const results = await Promise.allSettled(
    targets
      .filter(t => t.optedIn && t.healthy)
      .map(t => forwardWebhook(t, req.headers, rawBody)),
  );

  return summarizeResults(results);
}

Routing vs fan-out: two delivery modes

Not every webhook should reach every preview. The relay supports two modes:

Targeted routing

When the outbound request included a routing key — typically a run ID or job ID embedded in the webhook payload metadata — the relay delivers to exactly one environment. The preview backend registered that key when it initiated the external job.

// Preview backend registers intent before calling Replicate
await relayRegistry.register({
  routeKey: `run-${runId}`,
  environmentId: 'pr-142',
  webhookUrl: 'https://pr-142.preview.internal/api/webhooks/replicate',
  ttlMs: 3_600_000,  // auto-expire after 1 hour
});

// Replicate callback includes run ID in payload
// Relay extracts run-abc123 → forwards only to pr-142

Opt-in fan-out

For providers where routing keys are unavailable or for debugging, environments opt in to receive all callbacks of a given type. The dev stack is always opted in. PR previews opt in explicitly via a CLI flag or PR label.

Mode When to use Risk
Targeted routing Production-like flows with registered job IDs Miss if registration TTL expires before callback
Opt-in fan-out Debugging, integration testing, dev stack Duplicate processing if multiple envs opt in

Fan-out is intentionally opt-in, not opt-out. Early versions fanned to all active previews by default — forty environments processing the same Stripe test event caused race conditions and confused debugging sessions.

Signature verification forwarding

Webhook providers sign payloads with a shared secret. The relay verifies at the public boundary, then forwards the raw body and original signature headers to the target. Preview backends re-verify independently — defense in depth.

function forwardWebhook(
  target: RelayTarget,
  originalHeaders: IncomingHttpHeaders,
  rawBody: Buffer,
): Promise<Response> {
  const forwardHeaders = {
    ...pickSignatureHeaders(originalHeaders, target.provider),
    'X-Relay-Environment': target.environmentId,
    'X-Relay-Forwarded-At': new Date().toISOString(),
    'Content-Type': originalHeaders['content-type'] ?? 'application/json',
  };

  return fetch(target.webhookUrl, {
    method: 'POST',
    headers: forwardHeaders,
    body: rawBody,  // never re-serialize — preserves signature bytes
  });
}

Re-serializing JSON breaks signatures. The relay stores and forwards the raw body buffer untouched. This bit us once during development when an eager middleware parsed and re-stringified — HMAC mismatch on every forwarded webhook.

Opt-in mechanism for PR environments

PR previews register with the relay at deploy time. The deploy pipeline checks for an opt-in label or environment variable:

# PR preview deploy script excerpt
if [ "$WEBHOOK_RELAY_OPT_IN" = "true" ]; then
  curl -X POST "$RELAY_REGISTRY_URL/environments" \
    -H "Authorization: Bearer $RELAY_TOKEN" \
    -d "{
      \"environmentId\": \"pr-${PR_NUMBER}\",
      \"webhookUrl\": \"https://pr-${PR_NUMBER}.preview.internal/api/webhooks\",
      \"optedIn\": true,
      \"providers\": [\"replicate\", \"stripe\"]
    }"
fi

Deregistration happens on PR close — a GitHub Action removes the environment from the relay registry. Stale entries auto-expire via TTL regardless, but explicit cleanup prevents ghost forwards to torn-down infrastructure.

Health checks and unhealthy target skipping

Preview environments die without ceremony — PR merged, deploy failed, pod OOMKilled. The relay health-checks registered targets before forwarding:

async function healthCheckLoop(): Promise<void> {
  const targets = await registry.getAll();
  for (const target of targets) {
    try {
      const res = await fetch(`${target.webhookUrl}/health`, {
        signal: AbortSignal.timeout(5000),
      });
      target.healthy = res.ok;
      target.lastHealthCheck = new Date().toISOString();
    } catch {
      target.healthy = false;
    }
  }
  await registry.persist(targets);
}

// Runs every 60 seconds; unhealthy targets skipped until next pass

Failed forwards log to the relay's observability stack with environment ID, provider, route key, and HTTP status. The cost dashboard for the dev platform — tracking spend across dev stack and per-PR previews — includes relay forward volume as a line item, which surfaced one PR that opted in and processed 12,000 callbacks over a weekend.

Dev access controls: HUB_GATE_DISABLED escape hatch

Preview environments sit behind an auth hub in normal operation. For webhook forwarding and CI health checks, direct non-prod access must bypass the hub without disabling it globally.

The middleware exposes a HUB_GATE_DISABLED escape hatch — set per-environment, never in production — that lets internal service-to-service calls (relay → preview backend) skip interactive auth while browser traffic still routes through the hub.

Deploy-detection refresh banner

Webhook relay solved inbound callbacks. A related problem was outbound freshness: developers staring at a preview tab while a new deploy rolled underneath them.

The deploy-detection pattern adds a lightweight polling endpoint that returns the current deploy SHA. The frontend compares against the SHA baked into the loaded HTML:

// API route — no-store to prevent CDN caching deploy SHA
export async function GET() {
  return Response.json(
    { deploySha: process.env.DEPLOY_SHA },
    { headers: { 'Cache-Control': 'no-store' } },
  );
}

// Frontend banner component
useEffect(() => {
  const interval = setInterval(async () => {
    const { deploySha } = await fetch('/api/deploy-info').then(r => r.json());
    if (deploySha !== window.__DEPLOY_SHA__) {
      setShowRefreshBanner(true);
    }
  }, 30_000);
  return () => clearInterval(interval);
}, []);

HTML responses carry Cache-Control: no-store so the initial page load always reflects the current deploy. The refresh banner nudges developers to reload after push — preventing "my webhook handler isn't firing" reports that were actually stale JavaScript.

Operational considerations

Concern Mitigation
Relay becomes single point of failure Health-checked deployment, 2 replicas min, fail-open logging
Route key collision across PRs Prefix keys with environment ID at registration
Stale registrations after PR close GitHub Action deregistration + 1h TTL fallback
Signature mismatch on forward Raw body passthrough, never re-serialize
Runaway fan-out costs Opt-in only, per-environment forward quotas in cost dashboard

What I'd do differently

I would add a relay debug UI earlier. For the first month, forward failures were grep-through-logs debugging. A simple dashboard showing registered environments, last forward status, and route key mappings would have saved hours.

I would also enforce registration TTL more aggressively on targeted routes. A one-hour default seemed generous until a Replicate callback arrived ninety minutes later on a cold-start model — the registration had expired, the webhook hit dev stack instead of the PR that initiated the job, and the developer spent an afternoon thinking their handler was broken.

When you need a webhook relay

Build one when:

  • External providers allow only one or few registered callback URLs
  • PR preview environments need to receive real callbacks, not mocks
  • Signature verification must survive proxy forwarding
  • You want opt-in fan-out for debugging without exposing all previews by default

Skip it when previews can use mock webhook injectors, or when all external integrations support dynamic callback URL registration per request. Most GPU and payment providers do not.

The relay is boring infrastructure — receive, verify, route, forward. That boredom is the point. Developers testing webhook handlers on PR previews should not think about networking. They should opt in, push code, and watch callbacks arrive.
